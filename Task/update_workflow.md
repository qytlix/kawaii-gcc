# GCC 版本更新工作流

本文档描述了当 GCC 发布新版本时，kawaii-gcc 项目的同步更新流程。

## 一、触发条件

当满足以下条件时，启动本工作流：

1. GCC 官方发布了新版本（如 GCC 14、GCC 15 等）
2. 新版本包含本地化文件（.po）的更新
3. 项目维护者确认需要跟进新版本

## 二、代码适配流程

### 2.1 获取新版本本地化文件

**执行步骤**：
1. 访问 GCC 官方 SVN 仓库：`svn://gcc.gnu.org/svn/gcc/trunk/libstdc++-v3/po/`
2. 或从 GCC 源代码包中提取本地化文件
3. 获取以下语言的原始 .po 文件：
   - `zh_CN` - 简体中文
   - `zh_TW` - 繁体中文
   - `ja` - 日语

**输出文件**：
- `src/zh-origin-{version}.po` - 新版本原始简体中文
- `src/ja-origin-{version}.po` - 新版本原始日语（如存在）

### 2.2 分析版本差异

**执行步骤**：
1. 使用 `msgcmp` 工具对比新旧版本的 .po 文件：
   ```bash
   msgcmp src/zh-origin.po src/zh-origin-{version}.po > diff.txt
   ```
2. 识别新增的消息（msgid）
3. 识别删除的消息
4. 识别修改的消息

**输出**：差异报告文档，包含新增/删除/修改的消息列表

### 2.3 迁移可爱化补丁

**执行步骤**：

#### 2.3.1 处理已存在的消息
- 对于在新版本中仍然存在的 msgid，保留现有的可爱化翻译
- 使用 `msgmerge` 工具合并补丁：
  ```bash
  msgmerge -o src/zh_CN-kawaii-patch-{version}.po src/zh_CN-kawaii-patch.po src/zh-origin-{version}.po
  ```

#### 2.3.2 处理新增的消息
- 识别新版本新增的 msgid
- 为这些新消息添加可爱化翻译

#### 2.3.3 处理删除的消息
- 移除新版本中已删除的消息对应的补丁条目

### 2.4 更新项目配置

**需要修改的文件**：

| 文件 | 修改内容 |
|------|----------|
| `src/zh_CN-kawaii-patch.po` | 更新 Project-Id-Version 为新版本 |
| `src/ja-kawaii.po` | 更新版本信息 |
| `src/zh_TW-kawaii.po` | 更新版本信息 |
| `README.md` | 更新版本说明 |
| `README-zh.md` | 更新版本说明 |

## 三、测试验证步骤

### 3.1 构建测试

**执行步骤**：
```bash
make clean
make
```

**验证标准**：
- 构建成功，无错误
- 生成的 .mo 文件位于 `build/` 目录

### 3.2 功能测试

**执行步骤**：
```bash
cd test
./test.sh
```

**验证标准**：
- 所有可爱化消息正确显示
- 没有遗漏或错误的翻译
- 新版本的新消息也有对应的可爱化翻译

### 3.3 兼容性测试

**验证标准**：
- 在目标 GCC 版本下正常工作
- 不影响其他语言版本的功能

## 四、版本发布规范

### 4.1 更新 CI/CD 流程

**需要修改的文件**：
- `.github/workflows/test.yml` - 更新测试环境的 GCC 版本

### 4.2 发布检查清单

在发布新版本前，确保完成以下检查：

- ✅ 获取并更新新版本原始本地化文件
- ✅ 完成所有可爱化补丁的迁移
- ✅ 更新所有相关配置文件
- ✅ 通过构建测试
- ✅ 通过功能测试
- ✅ 更新文档说明
- ✅ 更新 CI/CD 配置

### 4.3 版本标签规范

使用语义化版本控制：
- 主版本号：跟随 GCC 主版本（如 GCC 15 → v15.x.x）
- 次版本号：补丁更新次数
- 修订号：小修复

## 五、后续维护

迁移完成后，建立定期检查机制：

1. **定期同步**：定期检查 GCC 官方本地化更新
2. **社区协作**：建立社区翻译贡献流程
3. **版本跟踪**：保持与 GCC 主版本的同步更新
